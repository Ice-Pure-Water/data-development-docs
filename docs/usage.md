# 使用指南

[返回首页](../README.md)

## 安装

本仓库根目录就是技能目录，使用时需保留 `SKILL.md`、`agents/` 和 `references/` 的相对位置。

对于使用 `~/.codex/skills` 目录的本地环境，可在目标目录尚不存在时执行：

```bash
git clone https://github.com/Ice-Pure-Water/data-development-docs.git ~/.codex/skills/data-development-docs
```

私有仓库需要有访问权限的 GitHub 账号。若使用自定义技能目录，将目标路径替换为该目录下的 `data-development-docs`。若已有同名技能，先对比并备份本地修改，再决定更新方式，避免覆盖个人规则。

让宿主重新加载技能后，通过 `$data-development-docs` 调用。具体加载方式以使用的宿主为准。

## 准备输入

优先提供现有资料的位置，而不是把所有内容重复粘贴进提示词：

| 输入 | 用途 |
| --- | --- |
| 需求、业务规则或已有文档 | 识别业务目标、范围与待确认口径 |
| SQL、ETL 代码、任务配置 | 还原实际加工步骤与依赖 |
| DDL 或可验证的 schema | 确认物理字段、类型、主键与粒度 |
| 目标表或消费方字段清单 | 以输出字段为入口组织血缘 |
| 交付阶段和目标路径 | 决定是否包含实施、运维和测试内容 |
| 验证查询、日志和结果（后期阶段） | 支撑实现状态与验收结论 |

资料不足时，先产出标注不确定性的文档草稿。将“设计中的字段”和“已核验物理字段”分开，业务口径不能靠猜测补齐。

## 场景一：目标方案

```text
使用 $data-development-docs，为当前 ETL 改造写中文目标方案。
以目标表字段为入口，读取项目需求、SQL 和 DDL，
输出 docs/solution.md 与 docs/solution.html。
覆盖业务规则、每个独立逻辑块及其图示、表关系和字段血缘，
说明全量/增量读取范围及软删除处理，保留待确认决策。
本次仅写方案设计，不包含开发进度或测试证据。
```

## 场景二：多份文档统一入口

```text
使用 $data-development-docs，把当前资料整理成中文文档集：
目标方案、开发进度、测试与验收，各自提供 MD 和 HTML。
增加 index.html 总览，提供端到端流程和每份文档的用途。
每个子页都能返回总览，导航顺序一致，并链接对应 Markdown。
仅依据实际代码和验证记录描述进度、结果，缺少的证据明确标注。
```

## 场景三：多源数据融合

```text
使用 $data-development-docs，说明多个来源如何加工为统一结果。
分别画出候选状态进入选举、非获胜源属性进入融合的路径。
列清每个属性的来源归属、取值/合并规则、保留路径与下游用途。
区分变化键发现和按键完整重算，并说明撤回及无候选结果时的清理。
生成配套 MD/HTML；所有示例表名以项目实际 DDL 为准。
```

## 场景四：更新已有文档

```text
使用 $data-development-docs，依据最新 SQL 和 DDL 更新已有方案文档。
保留项目术语、现有文档分工和已确认规则，先列出不一致之处，
同步修订 Markdown 与 HTML 的字段、逻辑块、图示及链接。
检查 HTML 结构、脚本语法和唯一 ID，并实际验证页面及一项交互；
环境不支持浏览器时，在交付说明中标记该项未完成。
```

## 阅读和验收

先从 HTML 总体流程进入具体节点，查看逻辑块、表关系和字段血缘；评审规则及维护内容时以 Markdown 为准。多页面从总览开始，按方案、进度、证据的用途进入。

交付时确认两种格式的事实一致，每个重要目标字段可追溯，每个独立计算有对应图示，图中连线表示真实关系。生成了 HTML 文件不代表已完成浏览器视觉验收，验证结论应如实记录。
