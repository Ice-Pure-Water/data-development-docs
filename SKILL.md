# 数据开发文档 · Data Development Documents

生成内容一致的两份交付物：用于编辑和评审的 Markdown 源文档，以及便于业务、开发、测试和项目管理阅读的自包含 HTML。Markdown 是内容事实源，HTML 负责导航、可视化和交互式阅读。

适用于数据加工方案、数仓模型、ETL 改造、字段血缘和多源融合说明。按交付阶段组织材料：方案设计聚焦目标规则，开发进度和测试证据单独呈现。中文使用说明见 [README.md](README.md)，完整操作示例见 [docs/usage.md](docs/usage.md)。

## Workflow

1. **Inspect the project first.** Read relevant project guidance, requirements, existing documentation, SQL/code, schemas, and available validation evidence. Prefer verified target schemas as the entry point for lineage. Reuse established terminology, table names, and conventions.
2. **Match the requested delivery phase.** For a solution/design-stage document, describe the target business behavior, architecture, tables, field lineage, constraints, and unresolved design decisions; omit whether work is implemented, execution results, test evidence, test cases, and release gates unless requested. For an implementation/operations-stage document, include code behavior and validation evidence when requested. Keep proposals, source requirements, and confirmed design decisions distinct.
3. **Define the document set before writing.** Decide which artifacts the request needs (for example, target solution, implementation progress, and test evidence) and identify the lifecycle phase each one describes. Keep stable target design separate from time-sensitive implementation status; never add current progress badges, environment snapshots, test outcomes, or open defects to a solution page unless the user explicitly asks for a combined document.
4. **Create a document hub when there is more than one HTML deliverable.** Use a hub-and-spoke information architecture: create one concise overview HTML as the entry point, then link to purpose-specific pages such as solution, progress, and test evidence. The hub orients readers, gives a small accurate view of the end-to-end data flow, and explains what each child page answers; it does not duplicate their detailed rules. Give each child page a clear route back to the hub and to related pages. Keep the repeated navigation items and their order the same across pages, use labels that identify the destination, and link each HTML page to its Markdown source. Read [references/document-hub-navigation.md](references/document-hub-navigation.md) when designing a multi-page document set.
5. **Build the Markdown source.** Explain the business outcome first, then scope and rules, solution/data flow, table responsibilities and relationships, and field-level lineage. For pipelines with source-state and elected-result tables that represent successive stages of the same record contract, require both tables to use the same typed entity-field set, types, and column order; their grain or keys may differ. Use the same field name for stage semantics (for example, `source` is the candidate source in source-state and the winning source in the elected result). Fields that are not produced until fusion remain present but null in source-state. Require every source-specific filter, mapping, deduplication/ranking, normalization, and source-only derivation to finish before writing that source's intermediate row. Separate source-local calculations from cross-source fusion in both the flow and lineage. Document both full and incremental/batch modes globally, with a per-stage and per-source filter/read-scope matrix: batch change detection may use source-specific batch markers, but recalculation for each affected key must read the complete current inputs needed by that source, and later election/fusion must read all source candidates for the affected key without blindly inheriting a raw source batch filter. For soft deletes, include tombstone rows in changed-key discovery, exclude deleted rows only when rereading current active source data, and retract a stale per-source intermediate when no active rows remain. Re-elect after the retraction; distinguish an explicit successful deletion from a computation failure, and define cleanup of stale final output when no candidates remain. In the elected-result layer, retain every non-key, non-winning-state attribute still needed by downstream rules, ADS, or audit, even when it comes from a losing or single source (for example, INPADOC event history). Specify each attribute’s owner, value, merge/selection rule, and result `other_info` path; preserve source provenance and do not copy only the winner source payload. Classify every intermediate field: put join/filter/group/order/partition and recurring batch-scan fields in typed entity columns; reserve JSON such as `other_info` for sparse source-specific passthrough, raw evidence, and low-frequency extensible details. Materialize computed lifecycle dates used by recurring scans (for example, the final expiry date) as entity columns in the layer that owns the fused calculation; preserve source-provided date candidates in source detail unless they themselves need frequent source-level filtering. State whether each field is verified in DDL or is a proposed logical addition. Include implementation, operations, and test/acceptance material only when the requested document phase calls for it; for solution-stage documents, exclude implementation state, execution results, test cases/results, and release gates.
6. **Decompose processing into logic blocks.** Give every distinct computation or processing operation its own documented logic block and corresponding diagram. Keep each block small enough to trace inputs, decisions, transformations, outputs, and affected fields/tables. Include acceptance checks only in implementation or test-stage documents. Name blocks with meaningful business or processing terms; use a concise readable name when diagram space is tight. Preserve existing project structure and terminology unless the user asks to restructure it. These are sections/visuals inside the paired MD and HTML deliverables unless separate files are requested.
7. **Build the HTML reading experience from the same content.** Keep Markdown as the source of truth for rules, tables, logic, and lineage. Preserve the Markdown content and semantic order in an HTML content library; render details from the matching source content rather than rewriting its facts. Present the HTML through progressive disclosure, not as a long article with extra navigation. For cinematic or animation-led requests, use one clear visual metaphor and one motion grammar. A suitable document pattern is an editorial opening followed by 5–7 concise story beats with one sticky process map; scrolling highlights the relevant nodes and edges, and selecting a node opens a contextual detail panel. Keep native scrolling reversible; use motion to explain movement, convergence, or decisions, never as decoration or a prerequisite for understanding. For a data-flow-first page, make one continuous, semantically accurate flow map the primary overview rather than a row or grid of stage cards. Keep the whole route visible as a locator while one stage expands; compress it into a readable mini-map during detail reading. The map must show source lanes, branch points, shared processing, convergence, and the output in their true order. Distinguish candidate/status flow from sidecar attribute flow: candidate streams enter election, the winner's selected fields continue downstream, and non-winning-source attributes follow their own documented path into fusion. Draw explicit merge paths into the fusion/output node; do not make crossing strokes or a shared color imply a merge. Use consistent source colors and line styles, route lines through whitespace, terminate each connector at its intended node, and layer node marks over connector intersections so the topology stays legible. Use particles only when they clarify direction; preserve a readable static path when motion is reduced or unavailable. Add an ADS-field explorer that highlights the selected field's source, transformation, responsible logic, and target. Keep global navigation visible and stable; dense detail navigation stays local to the detail view. For prose-heavy detail, use readable sans-serif body text, reserve monospace for identifiers and code, keep paragraphs to a readable measure, and split long explanations into titled chunks, callouts, or comparison tables. Avoid placing an entire schema or rule explanation in one code-styled paragraph. For dense tables, wrap long field values, set sensible column widths, and use horizontal scrolling only where necessary. For dense detail, use a large centered dialog with local section navigation and a separately scrollable content area; support close, Escape, and focus return. Make meaningful diagram nodes and connectors keyboard-operable and route them to the exact matching source section. Each detail needs a route back to its parent, the overview, and the document hub. If the user asks for a linear guided walkthrough instead, provide explicit previous/next/play/pause/reset controls with synchronized narration. Show only lifecycle/status labels that belong to the requested delivery phase; a solution-stage view presents target design without implementation or test-status badges. For progress overviews, present current progress, status, and update date/version as a display-only snapshot; do not add editing, owner assignment, browser persistence, or multi-person synchronization unless requested. Add implementation or acceptance evidence only when the requested phase calls for it. Keep interactions responsive, keyboard-operable, self-contained with inline CSS/JavaScript/SVG, and usable with animation disabled. Honor reduced-motion preferences. Avoid remote dependencies and do not imitate a named brand's exact assets or page composition. For table-relationship diagrams, model physical source tables, lookup/configuration tables, transformation steps, and output tables as distinct roles before arranging them; use the relationship-layout rules in [references/output-spec.md](references/output-spec.md).
8. **Cross-check the set.** Every material rule, table, field, logic block, diagram, and phase/status in each child HTML must match its Markdown source. Use unique semantic anchors and verify every cross-link. Confirm that the hub links to every requested deliverable and each child links back to the hub in the same navigation order. Confirm that implementation evidence appears only in progress/test pages, not the solution page.
9. **Finish with a concise handoff.** Name the hub and each paired MD/HTML deliverable, summarize their roles, and state any material evidence gaps. Do not claim visual/browser verification unless it was actually performed.

For the recommended section order, lineage columns, and HTML behavior, read [references/output-spec.md](references/output-spec.md).

## Reuse existing skills

- When the user asks to resolve data logic ambiguity or the processing rules are not yet settled, apply `data-grilling` for data profiling and business-rule questions. Reuse its evidence-first distinction: inspect facts available in files/schema/data yourself; ask the user only for business decisions. For ordinary documentation, use its nine categories as a completeness checklist without turning the task into an unnecessary interrogation. Preserve unresolved decisions as pending in the documents.
- When diagrams materially improve understanding, apply `diagram-design` for diagram selection and visual craft, then embed/adapt the relevant SVG or diagram into the HTML deliverable. Follow that skill's project style-guide setup instructions when they apply.
- When several HTML documents form one solution set, use the hub-and-spoke overview pattern and stable cross-page navigation described in [references/document-hub-navigation.md](references/document-hub-navigation.md).
- Use spreadsheet-specific skills only when the task actually reads or edits spreadsheet artifacts; use document-generation skills only when the requested artifact is a Word/PDF document.

## Completion criteria

- Both `.md` and `.html` exist at the requested or project-appropriate location.
- Parse the final HTML with an HTML parser and confirm the document skeleton is complete (`<style>` and `<head>` close before `<body>`), the visible application is inside the parsed body rather than stylesheet raw text, and the Markdown content library remains available. Check script syntax and unique IDs. If a browser can access the artifact under the active security policy, verify the rendered page and at least one interaction; otherwise state that visual browser QA remains incomplete.
- The document set explains the business outcome and processing approach, identifies involved tables and relationships, and traces each important target field to its sources and transformation rules.
- Every distinct computation or processing operation is documented as its own clearly named logic block and has a matching diagram; block inputs, outputs, decisions, and affected field lineage are traceable.
- The content matches the requested phase: a solution-stage document describes the target design and unresolved choices without implementation status or test material; later-stage documents may add evidence appropriate to that phase.
- Names, section order, tables, and evidence align across both files; HTML opens at the flow overview, every node and connector follows the correct semantic route, detail navigation can return to its parent and overview, and all content remains available without animation or external assets. For multi-source flows, verify candidate election and attribute fusion as separate paths and confirm each connector's source, target, and meaning. A solution-stage set contains no implementation-state or test-result sections unless requested.
