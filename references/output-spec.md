# Paired Output Specification

Use this as a flexible baseline. Omit sections that do not apply and add domain-specific sections when they improve decisions or delivery.

## Markdown structure

1. **Title and document status** — owner/date/version if known; identify the requested phase (solution design, implementation, operations). For solution design, keep the document about target behavior and design decisions.
2. **Executive summary** — business problem, expected outcome, users/consumers, and what changes.
3. **Scope and assumptions** — included/excluded work, dependencies, confirmed decisions, assumptions, and open questions.
4. **Business rules** — meaningful rule names; rule statement, rationale, examples/boundaries, and status.
5. **Solution flow** — source-to-output steps, decision points, timing/refresh behavior, and failure/recovery paths when relevant.
6. **Logic blocks** — give each distinct computation or processing operation its own clearly named block. Use concise meaningful names in diagrams when space is limited. For each block, document its purpose, inputs, outputs, ordered transformations/decisions, relevant business rules, affected fields/tables, and edge/null behavior. Include implementation failure handling and acceptance checks only when the requested phase includes implementation or testing. Include a dedicated diagram for that block; do not combine separate operations into one opaque diagram. A block and its diagram are dedicated sections/visuals within the paired MD and HTML files, not separate files by default.
7. **Table inventory and relationships** — table name, physical/logical status, purpose, grain, key fields, upstream/downstream links, and evidence source.
8. **Field-level lineage** — one row per important target field; see the schema below, with links to the named logic blocks that derive or populate it.
9. **Development notes** — transformation sequence, joins/filters/deduplication/aggregation, incremental or backfill behavior, and operational considerations supported by evidence.
10. **Test and acceptance, when requested by the document phase** — named checks tied to rules, blocks, tables, and fields, expected result, test data or query, and evidence/status. Omit this section from solution-stage documents.
11. **Glossary and decision log** — only terms and decisions needed to read or maintain this solution.

Recommended field-lineage columns:

| Target field | Target table.field | Business meaning | Source table.field | Transformation / rule | Join / filter / grain | Null, conflict, or default behavior | Verification / test (later phases only) |
|---|---|---|---|---|---|---|---|

Represent multi-source, derived, or conditional outputs explicitly. Distinguish direct mappings from derivations. Include SQL snippets only when they clarify a non-obvious rule; prefer a concise rule explanation plus a code/query pointer.

## HTML reading experience

- When the deliverable set contains multiple HTML pages, make a separate document overview the default entry point. Use the hub-and-spoke structure in [document-hub-navigation.md](document-hub-navigation.md): the hub orients and links to child pages without duplicating their detailed rules; each child links back to the hub and related pages through consistent global navigation. Keep solution, implementation progress, and test evidence on separate purpose-specific pages, with phase-specific status dates only on progress/evidence pages.

- For cinematic or animation-led requests, use one connected visual metaphor and one motion grammar. A document-friendly pattern is an editorial opening followed by 5–7 concise story beats with a sticky process map. Native scrolling advances and reverses the active scene; selecting a node opens contextual detail. Use motion to explain data movement, convergence, or decisions; keep the story understandable without autoplay. Add an ADS-field explorer that highlights source, transformation, responsible logic, and target. This is a visual pattern, not a requirement to copy any brand’s exact assets or page composition.

- Preserve the Markdown heading text, hierarchy, order, and content in a one-to-one mapping. Present it through progressive disclosure. The opening screen is an overall flow diagram plus a plain-language explanation of inputs, main transformations/decisions, and outputs. In solution-stage documents, do not show implementation or test status. Animate the real sequence in stages with synchronized narration, progress, play/pause, previous/next, and reset controls. Use lifecycle/status labels only when they belong to the requested phase; omit implementation and testing states from solution-stage documents. Clicking any flow node opens the corresponding detail; each detail offers a next level for its logic blocks, tables, and field lineage, with breadcrumbs/back navigation. Add acceptance evidence only for phases that request it. Keep the complete Markdown-derived content available as the HTML content library without silently removing or rewriting it. The overview animation should remain the default entry point, and details should reveal progressively from the selected node.
- Put a summary and contents near the top. Use clear section anchors, restrained color, readable type, and responsive layouts.
- Keep prose in readable sans-serif text and reserve monospace for identifiers and code. Break dense paragraphs into labeled blocks and keep line lengths readable. In tables, wrap long identifiers, size columns to their content, and use horizontal scrolling only when the table cannot reflow without losing meaning.
- Give every named logic block its own corresponding diagram showing that operation's inputs, steps/decisions, and outputs. Also use diagrams for overall process and table relationships when useful. Label data nodes with understandable names and real table identifiers. Keep detailed field logic in a searchable/filterable table rather than cramming it into the diagram.
- **Model table relationships before drawing.** Classify nodes as source tables, source-specific lookup tables, shared mapping/configuration tables, transformations, and targets. Preserve the physical table identity and the confirmed upstream/downstream relationships. An identifier-normalization table such as an application-number map belongs only on the source lane that uses it; place it between that source and the next processing step. Do not make it look like another raw source.
- **Represent shared mappings once.** Inspect the mapping configuration's source/dimension coverage instead of assuming each source has a separate mapping table. When several sources use the same physical mapping table, draw one shared table node, name the covered sources, connect each source lane to that node, then connect its mapped output to the shared source-state or target layer. Keep source-specific preprocessing (for example, identifier mapping) on only the relevant lane. If sharing is unconfirmed, mark it unresolved instead of inventing duplicate tables or shared behavior.
- **Lay out the graph in ordered stages.** Prefer left-to-right columns for source inputs, source-specific preparation, shared mapping/normalization, unified source state, cross-source selection, and final output. Keep source lanes in a stable top-to-bottom order. Route their connectors to target ports in the same order so lines do not cross at fan-in/fan-out points. Place priority dictionaries and other rule/configuration dependencies beside or beneath the step they govern, with a direct connector and a clear visual role; keep them separate from raw source rows. Use short orthogonal or gently curved paths, reserve space for long dependencies, and widen the canvas before accepting crossings. Arrowheads are optional; line direction can be made clear through placement and labels.
- **Render-check the actual diagram.** Inspect an SVG/HTML render at the size readers will see, including the detail panel and any cloned/modal view. Confirm that every connector touches its intended node, shared tables have all expected source links, source-specific maps stay on their own lane, and no paths cross, disappear under cards, or obscure labels. Check card text wrapping and horizontal scrolling at desktop and narrow widths. A semantic parser or node/edge count does not replace visual inspection.
- **Keep navigation global and details focused.** Use one document-wide contents/navigation system that stays consistent across story beats and detail views. Let overview nodes and meaningful connectors open the exact matching logic/table section. For dense tables and long logic, use a large centered dialog rather than a narrow drawer: place local section navigation beside a separately scrollable detail area, provide a visible close control and Escape handling, and return keyboard focus to the opening node. On narrow screens, adapt local navigation into a compact horizontal strip while keeping detail content readable.
- **Keep interactions attached to source content.** Use one Markdown-derived content library as the authority for both the full document and detail views. Route each SVG/HTML node by a stable section key plus an optional exact heading; support click, Enter, and Space. If detail content is cloned, rewrite IDs and internal references so anchors and SVG definitions remain unique and work in both the library and dialog. Verify a node and a connector route in the rendered page, not only by checking that route attributes exist.
- Make HTML materially more useful than a print-style rendering by making the overview animation and drill-down the primary interaction. Field-lineage selection should reveal its source, transformation, target, and evidence; where references can be matched, cross-highlight the relevant logic, table, diagram, and acceptance content. Keep all labels understandable when animation is off. All detail screens need a visible route back to their parent and the overview.
- For solution-stage documents, label design decisions as confirmed or pending where useful, and leave implementation and test state out. For implementation-stage documents, distinguish confirmed, observed, inferred, and pending evidence; do not encode status by color alone.
- Keep CSS, JavaScript, and SVG inline when feasible so the HTML can be opened locally and shared as one file. Avoid remote fonts, scripts, and image dependencies by default.
- Include a short note that Markdown is the editable source when the two files are maintained manually. If generated from shared structured content, describe the generation command instead.

## Consistency checks

- Compare headings, tables, fields, rules, logic blocks, and phase-appropriate acceptance checks across both files; ensure generated anchors are unique and resolve. Use meaningful visible names rather than artificial document codes. Preserve true data identifiers such as physical table names, field names, and domain status codes.
- Inventory every distinct computation/processing operation and verify a one-to-one correspondence between its named description and dedicated diagram in both files; ensure anchors and cross-links resolve.
- Check that each important output field has a source or an explicit origin such as constant, rule-only derivation, or unresolved source. Check that HTML interactions are keyboard accessible, work offline, do not alter source content, and respect reduced-motion settings.
- For solution-stage documents, ensure important business rules map to named solution logic blocks and fields; do not require implementation descriptions or acceptance checks. For implementation or test-stage documents, connect rules to evidence and checks.
- Preserve qualifiers: physical DDL vs logical design, observed data vs expected behavior, and verified evidence vs assumption.
- If only one artifact can be completed because of missing evidence, produce the useful draft pair with the uncertainty marked; report exactly what remains unresolved.


## Intermediate field allocation

For successive source-state and elected-result tables representing the same record contract, require an identical typed entity-field set, types, and column order; keys/grain may differ. Document stage-specific meanings and nullability (for example, a result-only field remains present but null in source-state). Provide a field allocation matrix that separates typed entity columns from JSON `other_info` payload. Entity columns should include keys, values used in joins/filters/grouping/order, batch metadata, and recurring-scan fields. Keep sparse source-specific passthrough, raw evidence, and low-frequency extensible attributes in `other_info`. Complete source-local filtering, mapping, deduplication/ranking, normalization, and derivations before inserting a source-state row; reserve cross-source election and fusion for the later result layer. Promote a fused lifecycle date such as final `expiry_date` to an entity column in the layer that computes it when periodic batches filter on that date. Mark proposed logical columns separately from verified physical DDL.


## Elected-result attribute fusion

An elected-result table must not inherit only the winning source's payload. Inventory non-key and non-winning-state attributes from every source that downstream rules, ADS, or audit still need, including attributes unique to a losing source. For each, document source ownership, value selection/merge semantics, provenance, and the exact result `other_info` path. Preserve event-level details when later processing depends on them; use namespaced source subobjects plus normalized merged values where both traceability and downstream use are required.


## Full and batch processing scopes

Describe full and batch modes side by side. Provide a step-by-step matrix that separates source-specific change detection from per-key recomputation, election, post-processing, and writes. Do not propagate one batch marker indiscriminately through all stages. After a key is marked affected, reload that key's complete current source inputs (including full history where required); election and attribute fusion must consider every source candidate for that key. Include non-source triggers such as expiry-date scans in the affected-key union. Identify missing or unverified source change markers explicitly.


For source soft-delete flags, the incremental changed-key scan must include deleted rows before the active-row filter. Then reread complete current records for each changed key, excluding deleted rows; if none remain, retract the stale source-state row and rerun downstream election. Keep this separate from source computation failure, which must not be mistaken for a valid deletion. Define what happens to the elected and consumer rows when explicit deletion leaves no candidates.
