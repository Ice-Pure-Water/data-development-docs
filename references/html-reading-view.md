# 数据方案规格 Markdown 与 HTML 生成规范

本规范用于把不同业务的方案 Markdown 先整理为统一的数据规格 Markdown，再从规格 Markdown 生成适合展示、讲解、逐层阅读的 HTML。它规定规格内容结构及可复用的页面关系、交互和视觉约束；业务事实、阶段数量、对象角色、适用范围和术语必须按当前输入重新抽取，不得照搬其他项目。HTML 的文字层级、分区排版、中文换行和可读性验收统一按[文字展示方法](text-display-method.md)执行。

## 规格 Markdown 结构

规格 Markdown 是本流程的规范化产物，也是 HTML 唯一的内容基线。先将一份或多份方案 Markdown 中的事实按适用的数据规格规则重组为 Markdown，再生成 HTML；不要跳过规格 Markdown 直接从零拼 HTML。若用户提供了专门的规格模板或规则文件，以用户提供内容为准；否则使用本节结构，并根据实际内容增删小节，不得为了填模板而编造信息。

推荐的通用章节顺序：

1. **方案标题与摘要**：明确业务对象、目标、核心数据流和结果。
2. **需求与参考来源**：需求文档、外部参考、来源方案 Markdown；保留可点击链接或来源定位。
3. **整体数据流程**：描述阶段顺序、分支、并行、汇合及输入输出关系。
4. **阶段处理方案**：逐阶段说明业务目标、处理逻辑、读写对象和阶段间关系。
5. **独立业务规则**：完整列举可单独讲解的判断，说明条件、处理、结果、例外和待确认项。
6. **数据对象**：按角色与适用范围说明来源、配置、中间、结果等对象；库名、表名、用途及必要的 DDL 对应关系。
7. **字段血缘**：逐目标字段说明业务含义、来源、推导、阶段及边界。
8. **术语与待确认事项**：只在来源确有需要时保留。

来源中的规格事实须在重组时保持含义不变。对重复内容去重，对冲突口径并列标注待确认；重要规则、数据对象和字段信息标出来源章节/文件或链接。规格 Markdown 不纳入实现 SQL、测试验证、进度、运行/部署状态、发布运维或数据使用者说明。不要把 HTML 生成说明写进业务规格正文。

## 稳定内容模型

生成 HTML 前，先从输入 Markdown 建立规范化内容清单（canonical manifest），再由同一份清单生成阶段导航、纵向流程图、阶段详情、读写对象、业务逻辑专题、数据对象行列分区和字段血缘，避免重复手工维护导致关系漂移。清单至少包含标题摘要与来源链接；有序阶段、节点、前后关系、详情和读写对象；节点与数据对象的输入输出关系；全部独立业务逻辑及关联阶段；数据对象角色、输入中明确的适用范围、用途和 DDL 关系；字段血缘；未决口径及来源。

阶段、逻辑和对象使用仅供锚点联动的稳定内部键，不在画面中展示技术 ID、代号或人为编号。键名、标题和交叉引用须从同一清单生成。数量、名称和范围维度一律从当前输入取得，不预设固定值。

### 阶段、Markdown 与主图一致性契约

- 从规范 Markdown 的阶段标题、整体流程关系和阶段处理内容抽取 canonical manifest。它是所有 HTML 展示区域的唯一中间模型；不得分别手写阶段目录、图节点和详情标题。
- 每个阶段在 manifest 中只有一个稳定内部键、一个中文标准名称、一句摘要、一个 Markdown 来源锚点、读写对象集合和完整详情。左侧阶段导航、主图阶段区域、右侧详情、滚动锚点和专题引用均由这些记录生成。
- 一个阶段可以有多个并行节点，但每个节点都带相同阶段键，并归入同一阶段背景区域。节点标题使用阶段标准名称或其明确的处理子项名称。没有独立处理阶段的配置对象，关联到其真实作用阶段。
- manifest 的每个数据流关系都映射到主图或明确关联的阶段细节图。若为满足 diagram-design 预算而在总览中抽象关系，细节图保留被抽象的关系并链接回对应阶段；不得省略关系或将不同路径画成错误的单路径。
- 生成后核对：Markdown 阶段键集合、导航键集合、主图阶段键集合、详情键集合一致；节点/边与 manifest 一致；所有导航、节点及专题锚点定位正确；无缺阶段、孤儿节点/详情、错误链接、重复键或无图可查的数据关系。
- 完整 Markdown 页面和讲解主页从同一规范 Markdown 生成。主页可以按阅读层级重组，但所有摘要、阶段、业务规则、数据对象和字段关系都追溯到同一内容模型。

阶段导航、总图阶段区域、右侧详情和节点定位必须一一对应。图中连线须对应输入明确的数据对象关系或处理关系，不得虚构依赖。阶段读写对象与对象清单共用对象记录；未说明读写关系时标“待确认”。字段血缘仅采用 Markdown 或明确关联 DDL 支持的信息，不从 SQL、代码或运行库推测。

## 主页面固定顺序

1. **标题和摘要**：中文业务标题；摘要只说明目标、核心数据流和结果对象。
2. **需求与参考链接**：紧接标题摘要，显示可点击的需求来源和外部参考。链接名称使用业务可理解的中文。项目处理 SQL 不出现在页面；用户明确要求保留外部参考 SQL 时，只显示外部参考链接，不展示代码。
3. **整体流程讲解**：页面视觉主体，左侧阶段栏、中间完整的纵向流程图、右侧当前阶段业务详情与对象读写说明。主流程自上而下；并行来源可在同一层横向并列，随后向下汇合。
4. **关键业务逻辑**：紧随整体流程。把 Markdown 中所有能独立讲解的业务判断分别列项，不能只挑几条，也不能把不同条件揉成概览卡片。结论标题和一句摘要常显；详情在当前页原位展开。
5. **数据对象**：独立于流程图。按二维关系呈现：行表示对象作用，列表示适用范围。按输入识别的来源、配置、中间、结果等角色作为行；按输入明确的环境、阶段、地域或版本等范围作为列。各交叉区逐项标出库名、完整对象名、用途、粒度/主键和 DDL 对应关系。视觉上使用对齐的行列分区和细分隔线，不用 HTML 表格或卡片。
6. **字段血缘**：按输出表字段列出含义、来源、推导、阶段、空值和冲突处理。
7. **来源说明**：提供 Markdown 来源和相关 DDL/需求链接。

主页面只做数据方案展示。排除实施步骤、处理 SQL 内容、测试/验证、进度、运行状态、发布运维和数据使用者说明。

## 流程讲解布局

### 三栏结构

- **左栏：阶段导航。** 每阶段展示序号、阶段名称和一句摘要。使用垂直细线/节点建立阶段序列；当前项同时用清楚的浅底色、可见侧边强调线、深色文字和较粗字重突出，不得仅靠微弱颜色变化提示。
- **中栏：整体数据流程。** 展示覆盖全部阶段的 SVG 主流程总览，优先纵向自上而下；来源并行分支在同层呈现后再汇合。按 diagram-design 复杂度预算拆分时，仍保留贯穿全部阶段的端到端总览，并用关联的局部图补足被简化的来源分支、属性路径和处理关系。所有源文档关系都必须映射到总览或细节图中。不得在节点内塞库表清单。
- **右栏：阶段详情。** 显示阶段名称、摘要、业务细节和此阶段读写对象。来源并行处理或同层规则应同时可见，避免只显示被拆开的单一路径。

### 滚动与联动

- 在流程区设置长滚动轨道和 sticky 三栏视图：桌面端顶部偏移可从约 78px 起调，视图高度为 `calc(100vh - 78px)`。轨道长度按实际阶段数和阅读节奏计算，不能固定假设阶段数或使用固定 500vh。
- 页面滚动依据轨道进度切换当前阶段。左侧 `aria-current`、右侧详情、图中对应阶段浅色带和该阶段全部节点同时更新。当前区域须一眼可辨；背景带覆盖阶段区域，当前节点边框加粗但维持原语义配色，非当前节点不得灰化或降低对比度。流程区结束后恢复普通页面滚动，继续到关键逻辑、数据对象分区和血缘。
- 点击左侧阶段或图中节点可定位相应阶段；键盘 Enter/Space 可触发。焦点样式清楚，锚点预留 sticky 顶栏间距。
- JavaScript 关闭或不可用时，所有阶段详情应仍可访问；不要让内容依赖 JS 后完全消失。
- 本 HTML 仅面向电脑端展示，不设计手机或窄屏响应式布局。按总图、导航、详情的实际宽度扩展页面版心；流程图必须完整显示在流程栏内，流程图容器不得出现横向滚动条或要求读者左右拖动。视口较窄时允许浏览器对整页进行横向滚动，不能把横向滚动藏在流程图内部。

### 总图拓扑与连线

- **流程图以 [diagram-design](diagram-design-integration.md) 为规范来源。** 整体数据架构使用 Architecture，遵循其复杂度预算、布局、语义节点、颜色、正交路由、端口、跨线、SVG 和动效规则；执行顺序与数据规格适配方式见[数据规格图执行规则](flow-diagram-method.md)。从当前规格 Markdown 重建节点/边清单，禁止从旧 HTML 复制业务拓扑。
- 本页面特有的联动约束继续适用：完整纵向总图贯穿讲解区；阶段导航、当前阶段详情和总图同进度；当前阶段只增加清楚可见的低饱和背景带，节点和线条本身语义配色不变、不灰化。
- 用户确认的流程图例外是连接线不带箭头，以沿每条连线流动的短线段表达方向；禁止以单个移动光点代替线动效。其他连线、配色、线宽、交叉和动效行为依 diagram-design。静态连线始终完整可见；减少动态效果或打印时隐藏流动线段，保留完整静态图。
- 节点标题和辅助文字需要在最终 SVG 尺寸下检查；中文换行或扩框，不能溢出。每条流动线段与对应静态路径完全重合并沿数据方向移动。`prefers-reduced-motion: reduce` 时停止动效但保留完整静态路径；无脚本时仍可读。

## 独立逻辑专题

- 规则抽取以 Markdown 中每一项有独立条件或结果的判断为单位。同一主题下存在多个独立条件或结果时，分别建立专题；只有语义和适用边界都完全相同的条目才合并。
- 每项用原生 `<details><summary>`，summary 始终可见并包含：短序号/组别、结论式标题、一句摘要。展开内容包含条件、动作、结果和例外/待确认点；一个 block 只讲一个逻辑。
- 电脑端两列排版，以细分隔线组织，不做卡片墙。展开在原位发生，不打开侧栏、不跳转、不覆盖其他逻辑。
- 专题数量由输入内容决定，不能规定“最多几个”或只挑选代表项。每条都要回到对应流程阶段，并与阶段详情内容一致。
- 详细规格页存在时，专题仍是主页独立讲解入口；点击专题不会离开主页。

## 数据对象行列分区与字段血缘

### 数据对象行列分区

- 行按对象作用分类，常见有来源、配置、中间、结果；列按输入中的适用范围组织，例如正式/测试、开发/生产、地域或版本。不要预设固定列值。
- 使用 CSS Grid 等布局原语呈现一块真实的二维矩阵：第一行为列标题，后续每行对应一种对象作用；每个对象必须落在其来源文档声明的适用范围列。用语义化行列标题和细分隔线保持对齐，交叉单元格用普通列表承载对象，不使用 HTML `<table>`，不做卡片。禁止把矩阵退化成“来源对象/配置对象/中间对象/结果对象”四段纵向列表。
- 一个适用范围时可保留单列并明确列名；范围未说明时标“适用范围待确认”，不虚构列。没有对象时标“未列对象”或“待确认”。
- 每条写清库名、完整对象名、用途；粒度、主键、所处阶段和 DDL 关系仅在输入提供时展示。对象名完整可读可复制，长标识自然换行，不裁切省略。
- 明确区分“方案目标”与“DDL 定义对象”，名称不一致时并列说明并标记待确认。
- DDL 链接指向现存 DDL 文件；绝不引用已停用/被弃用的结构文件，除非用户明确要求比较。

### 字段血缘

- 一行一个输出字段。最少列为：字段、来源与推导、处理阶段、空值/冲突边界。原规格更完整时保留所需信息，不把不同字段合并到同一行。
- SQL/代码文件名不得充当字段来源；用库表字段、业务规则、映射或常量表达来源。未知口径写“待确认”。

## 完整规格页（仅用户明确要求时）

- 完整规格页由同一 Markdown 转换，主页导航标“完整规格”，完整页导航提供“方案概览”返回。
- 保留所有**范围内**规格细节并按章节阅读；范围外的实现、测试、进度和部署材料仍应剔除。不要复制主页的三栏讲解作为第二套布局。
- 适用章节可包括：用途与范围、整体方案与数据流、业务规则、处理逻辑方案、输出字段血缘、库表与配置、JSON 字段契约、术语。
- 按来源内容保留适用的详细规则表、优先级/枚举映射、处理规则、字段血缘、对象字段定义和配置契约；不预设特定业务的映射类型或环境名称。
- 长规格页用窄侧边目录 + 宽阅读正文。目录点击定位章节；顶部栏 sticky。长表格可以单独横向滚动；整体数据流程图不允许局部横向滚动。

## 中文、术语和标题

- HTML 中的文字角色、字号层级、正文行宽、段落节奏、技术标识换行及分区域排版以[文字展示方法](text-display-method.md)为准；本节只定义术语和事实表达，不重复制定第二套排版规则。
- 用业务上下文中的自然中文，不把英文术语硬译成生僻名词。相同概念全页固定一个中文名；表、库、字段、代码值和产品名保持原样。
- 标题说明业务对象和方案内容，不以 HTML、页面结构、版本号或内部代号命名。
- 摘要下方仅放与方案有关的内容和来源链接；不写文档面向角色或系统功能介绍。
- 条件、优先级、数值、日期边界、冲突、空值、fallback 都要保留；口径不一致显式标为待确认。

## 固定视觉基线

- 输出为自包含 HTML：内嵌 CSS、SVG 和必要 JS，不用 CDN、远程字体、外部脚本或运行时构建。页面语义使用 `header/nav/main/section/aside/footer`，链接、表格、`details` 使用原生元素。
- 采用浅灰蓝页面底色（主参考 `#f5f7fa`）、深蓝灰正文（`#17243a`）、白色阅读面、低对比度分隔线（`#d9e2ec`）。电脑端主容器按内容扩宽，通常约 1800–2000px，左右留白约 32–40px；总图所在栏应能容纳完整 SVG。
- 顶栏高约 60px，sticky，半透明白底和底部分隔线；主导航可横向滚动，不得被父容器裁切或随下拉消失。
- 文字角色、字号、行宽、行距和中文换行以[文字展示方法](text-display-method.md)为准；对象名使用等宽字并仅在长技术标识需要时应用 `overflow-wrap:anywhere`。
- 流程节点类型、配色、字体、描边和强调按 diagram-design 的 Architecture 规范及其 `style-guide.md` 执行；不按来源类别堆叠彩虹色。正文采用清晰层级，避免过度渐变、装饰插画、仪表盘和卡片墙。
- 专题区桌面两列，细线分隔；数据对象区使用“作用行 × 范围列”的对齐分区，轻量分隔行列，不加卡片边框、不使用 HTML 表格；血缘表格清楚易读。
- `:focus-visible` 有明显焦点框；颜色不单独承担信息含义；固定定位不遮挡锚点。

## 转换完成清单

- [ ] 标题和摘要只介绍业务方案；来源链接可点击且归属清楚。
- [ ] Markdown 阶段、左栏导航、主图阶段区域、右栏详情和专题锚点由同一 manifest 生成并逐键核对；总流程纵向自上而下，阶段路径真实表达并行分支、汇合和输出。
- [ ] 主流程图没有箭头或单独光点；每条关系都有沿真实方向移动的线段和完整静态底线；其余线条和跨线处理符合 diagram-design；减少动态效果或打印时静态路径仍清楚。
- [ ] 逐一检查节点、连接线、标签、端口和交叉；按 diagram-design 的正交布线和 bridge/hop 规则处理，几何交叉不得误表示数据汇合。
- [ ] 所有可独立讲解的业务规则均有独立专题，不限数量；每项有结论标题、摘要和完整条件/结果/边界。
